### Shipping

Resolve the driver skill through [poteto-mode's Non-negotiables](../SKILL.md#non-negotiables).

You own what lands. Land one independently verified PR at a time, confirm its outcome, and leave the remaining chain alone. This follows `playbooks/babysit.md` and requires explicit user landing authority. Autopilot's operator-controlled merge gate still applies.

1. **Resolve the forge and chain.** Default to `gh`; use Origin only when its installed service resolves the repository and supports the required safety conditions. Record the choice, never require `gt`, and leave unrelated PRs alone. Capture the chain bottom-to-top with head branches and SHAs, base branches and SHAs, and the destination repository and branch. Read [Merge and restack safety](../references/merge-safety.md) before any merge or topology operation. Inspect existing pending requests and cancel those without step 8's durable gates before a lengthy review.
2. **Verify each PR independently.** Dispatch one verifier per PR through native delegation, with an isolated checkout where execution writes. The verifier must not have authored the code. It compares parent against head through the project's matching driver and posts `PASS`, `PASS+NOTES`, or `FAIL` with the behavioral evidence and independent correctness review. Green CI and approving bots do not replace that verdict. Record the reviewer, head SHA, base SHA, base branch, and stable base-to-head `git patch-id`.
3. **Find the contiguous verified run.** Start at the lowest unmerged PR and stop at the first without a passing verdict. Report the ceiling. A verified child above an unverified parent waits. If it truly neither holds nor needs its parent's code, the topology owner may move it to trunk under the safety reference, but it needs a fresh verdict against that new context before landing separately.
4. **Cancel pending merges before changing topology.** Identify every affected PR, including descendants. Run `ship-pr inspect` and `ship-pr cancel-pending` per the safety reference, requiring a successful `cancelled` result for each before any rewrite, branch push, or base edit. This checks both automatic requests and queue membership with revision readback. Origin requires a validated equivalent, not this GitHub-only command. Failure, unavailable state, or a racing merge stops the rewrite until reconciled. Coordinate one topology writer so nobody rearms the chain meanwhile.
5. **Prepare only the bottom PR.** Fetch trunk. After a parent squash, replay only the child's own commits using the recorded old-parent boundary, not the new squash SHA. Publish with an explicit lease against the remote SHA captured before the rewrite and retarget only this PR to trunk. Do not prepare or arm descendants.
6. **Reassess every changed revision or destination.** Compare current patch and context with the recorded verdict. A matching patch-id can preserve substantive review after a history rewrite, not applicability to different dependencies or a new destination. Re-verify changed behavior or uncertain applicability. Always run current checks and mergeability after rewriting or retargeting.

   For changes only to tests, docs, or lint config, a lane may carry forward only when its executed artifact builds identically apart from demonstrated noise. Build twice at the verdict SHA and once at the new head. A difference counts as noise only if it also occurs between the two baseline builds or is an embedded commit SHA. Judge each difference, report its kind and files, and review the actual change with fresh checks. A lane with no build output, such as a dev server, must rerun. Capture the exact head and destination now approved.
7. **Request an immediate merge with a server-side head guard.** On GitHub use `gh pr merge <pr> --repo <owner/repo> --squash --match-head-commit <verified-head>`. Confirm the destination immediately before requesting it. This guards the head, not the base branch atomically. If retargeting cannot be controlled, resolve ownership first. Origin must prove an equivalent installed CLI or API condition; never guess a flag or merge unguarded. If unavailable, stop at merge-ready or explicitly resolve a supported forge path.
8. **Treat auto-merge and queue admission as future actions.** Require existing repository rules that enforce independent verification and required CI for the revision and context that will land, including invalidation of stale approval. A head check at admission is not enough. Never change protection settings or use `--admin` to bypass this gate. Without durable gates, watch for an immediate guarded merge. If repository policy requires a queue, stop at the unmet gate.
9. **Watch without mutating the rest of the chain.** For GitHub run `skills/poteto-mode/scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom>`. For Origin use `origin pr view <pr> --checks --comments` and `origin pr checks <pr> --watch`, then reread state. Use native background-process or scheduler tools, not an assumed `/loop` wrapper or second sleep loop. At each delivered event compare the full landing revision, including base OID, through `ship-pr inspect` or a validated forge equivalent. Cancel stale requests and reassess. Only step 8's durable gates protect the interval between observations.

   Preserve watcher blocker reasons. Route conflicts and `behind-base` to the topology owner, threads and CI to the PR owner, and human approval gates to a wait per `playbooks/babysit.md`. Do not rearm an unchanged blocker. `WAITING`, including `merge-queue`, is not completion. Diagnose `TIMEOUT` and `status-query`; unknown state never permits a merge.
10. **Confirm the landing before advancing.** A successful command or watcher `COMPLETE` is not enough. Read merged state, approved final head, intended base, and merge commit; fetch the destination and confirm that commit is in its history. Inspect the resulting content. If any fact contradicts the approved record, stop the chain. Otherwise preserve the old parent head as the child's exclusion boundary and repeat from step 4 for the new bottom. A host retarget to trunk can be expected, but confirm it rather than blindly repairing or trusting it. Nobody else writes to the chain during landing.
11. **Stop at the ceiling.** Report confirmed landings and what the next unverified PR needs. Extending the run needs new independent verdicts.

**Reply:** the verified run and ceiling, verdicts with reviewer and head/destination records, pending requests armed or cancelled and read back, confirmed landings, and unresolved gates or service limits.
